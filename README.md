# Better Reply 首条引用

让麦麦在回复某个人时，**第一条文字消息必定引用对方的那条消息**；同一个人同一条消息的后续分段不再重复引用。

适用的典型场景：

```text
A 问问题 A
B 问问题 B

麦麦的发送顺序：
A1（引用 A 的提问）
A2
A3
B1（引用 B 的提问）
B2
B3
```

## 它解决什么问题

MaiBot 1.3.19 的引用不是由 Planner 或 Replyer 决定的，而是回复生成完之后，由核心 `src/maisaka/quote/rules.py` 按一套拟合公式随机抽签。配置里的「群聊引用频率 / 私聊引用频率」只有三档：

- 不引用：概率 0
- 偶尔引用：公式基础概率 × 1
- 经常引用：公式基础概率 × 2

**「经常引用」不是「总是引用」**。常见情况下概率只有 8%–46%，所以即使调到「经常引用」，群里也经常看不到引用。写进行为风格更没用——模型根本没有控制引用的参数（1.3.9 有 `set_quote`，1.3.19 已删除）。

本插件在发送前把核心算出的最终 `set_reply` 覆盖掉，所以能做到 100%：

- 同一个（会话，目标消息）在去重窗口内的第一条**文字**消息 → 强制引用；
- 同一目标的后续分段 → 强制不引用（避免 A1/A2/A3 每条都带引用）；
- 纯表情、纯图片、纯语音消息跳过，不占用「首次引用」名额；
- 换一个人提问（新的 `msg_id`）→ 重新引用。

## 它是怎么“劫持”引用的

不是改核心的概率公式，也不是改配置。

插件订阅 `send_service.before_send`（发送前最后一个可改参的 Hook），这个 Hook 能拿到：

- `set_reply`：核心抽签的最终结果；
- `reply_message_id`：本次发送要引用的目标消息 ID；
- `message`：待发送消息的序列化内容。

插件按 `(session_id, reply_message_id)` 维护一个带 TTL 的去重表：

- 第一次看到这个目标，且这条消息包含文字 → 把 `set_reply` 改成 `True`；
- 同一目标在窗口内再次发送 → 把 `set_reply` 改成 `False`；
- 目标换了 → 重新按第一次处理。

核心仍会在监控里记录它自己算出的 `quote_probability`，但实际发送以插件改过的 `set_reply` 为准。

## 安装

1. 把整个 `BetterReply` 文件夹复制到 MaiBot 的 `plugins` 目录：
   - Docker 部署通常是挂载出来的 `data/MaiMBot/plugins`；
   - 本地一键包通常是 `MaiBot/plugins`。
2. 打开 WebUI → 插件管理，启用「Better Reply 首条引用」。
3. 重载插件（或重启 core）。
4. 在插件日志里确认出现 `[BetterReply] 已加载`。

## 配置

`config.toml`：

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `plugin.enabled` | `true` | 插件总开关 |
| `quote.enabled` | `true` | 关闭后完全退回核心的随机引用 |
| `quote.ttl_seconds` | `300` | 同一目标消息的滑动去重窗口；连续分段只有第一条引用，停发超过该窗口后再次回复会重新引用 |
| `quote.max_entries` | `1000` | 内存中最多保留多少条去重记录 |
| `quote.platforms` | `["qq"]` | 生效平台；留空表示所有平台 |
| `quote.only_group` | `false` | 只处理群聊；关闭时私聊也生效 |
| `quote.force_no_quote_after_first` | `true` | 同一目标的后续文字消息强制不引用 |
| `quote.log_decisions` | `true` | 在插件日志里记录每次 `first=True/False` |

`ttl_seconds` 建议保持 300 秒左右：同一次回复的分段通常几秒内发完；如果麦麦隔了很久又回复同一条消息，会重新引用一次。

## 建议的行为风格（可选，但推荐）

插件负责「只要调了 reply，第一条文字就引用它的 `msg_id`」；它不负责判断「这几句应该回给谁」。如果麦麦把两个人的答案合并进同一次 `reply` 调用，一次调用只有一个 `msg_id`，插件也只能引用一个人。

所以建议在 **行为风格**（设置 → 人格 → 行为风格）里加一段：

```text
群里有多个人的问题需要回复时，必须按人分别调用 reply：先处理 A，msg_id 填 A 提问的那条消息；A 的后续补充继续用同一个 msg_id，但不要重复引用；处理完 A 再处理 B，B 的第一条同样引用 B 的消息。禁止把两个人的答案合并进同一次 reply 调用。
```

注意：

- 这段话是给 Planner 看的（行为风格只进 Planner，不进 Replyer）；
- 它不是为了“让模型记得引用”——引用由插件强制；
- 它是为了减少「两个人的答案挤进同一次 reply」的情况，让插件有机会按人分别引用。

## 限制

- **不能替模型拆答案**：一次 `reply` 调用只有一个 `msg_id`；合并回答时插件只能引用其中一个目标。
- **引用的是 Planner 选的 `msg_id`**：如果模型把 `msg_id` 指错了消息，插件会忠实地引用错的那条。
- **卡片/小程序目标需要实测**：强制引用一张分享卡片时，适配器可能不支持，极端情况下会导致该条发送失败；遇到就把该聊天排除或反馈。
- **纯表情/图片/语音不引用**：插件只认文字段；如果第一段是纯表情，会等第一条文字消息再引用。
- **插件重载后状态清空**：重载后的第一条回复会重新引用一次，属正常现象。
- **会影响其他插件带 `reply_to` 的文字发送**：任何带目标消息的文字发送都可能被当成“第一次引用”；如果某个插件先发了一条文字，麦麦自己的回复可能就不再引用。遇到这种情况可以按平台/群聊缩小 `platforms` 或 `only_group` 范围。

## 验证

- 插件日志（WebUI 插件日志或主日志里的 `[BetterReply]` 前缀）应出现：
  - 新目标第一次：`first=True set_reply=True`
  - 同目标后续：`first=False set_reply=False`
- 群里看效果：每一轮回复的第一条文字应该带引用框，后面几条没有。
- 如果日志有 `first=True` 但群里没有引用：大概率是该消息类型（卡片/小程序）不支持引用，或被适配器拒绝。
